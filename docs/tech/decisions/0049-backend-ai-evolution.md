# 0049 — 현재 백엔드 유지와 단계적 AI·RAG 확장

- 날짜: 2026-09-15
- 상태: 채택 (현재 방향). 후속 서버·언어·프레임워크 선택은 미결정
- 근거: 사용자와 기술 스택 대안을 검토한 뒤 문서화 요청. Java는 필수 조건이 아니며 특정 언어로의 이전을 요청한 것이 아니다.

## 배경
Finvesting의 목적은 본인이 실제로 사용하는 로컬 개인 금융 터미널이다. 이미 Next.js 안의 tRPC API가 계좌·거래·계산·DB·AI 호출을 담당하는 백엔드다. 별도 Spring Boot나 FastAPI가 없다는 것은 백엔드가 없다는 뜻이 아니다.

현재 투자 대비 효과가 큰 작업은 금융 계산·저장 정확성, 파일 가져오기와 복구, 수집 데이터 품질, 근거 있는 AI 설명이다. 언어 전환을 먼저 하면 API·계산 로직·DB 접근 이전과 재검증 비용이 추가된다.

## 결정
1. 기본 구조는 Next.js/React + TypeScript/tRPC + PostgreSQL/pgvector + 독립 worker + Ollama를 유지한다.
2. Java, Python, Spring Boot, Spring AI, FastAPI, LangChain, LangGraph는 필수 스택으로 지정하지 않는다. 기술 도입 자체를 목표로 삼지 않는다.
3. core는 금액·손익을 결정적으로 계산한다. AI는 검증된 계산 결과와 검색 자료를 설명하며 금융 원장을 임의로 수정하지 않는다.
4. RAG는 우선 기존 패키지 경계 안에서 구성한다. API가 DB 조회와 사용자 접근 범위를 조합하고, ai는 모델 호출과 프롬프트를 담당한다. DB 접근을 core나 웹 클라이언트에 넣지 않는다.
5. 개인 금융 데이터의 로컬 처리 원칙을 유지한다. 외부 모델 도입은 별도 데이터 전송 범위 검토와 결정이 필요하다.

## 용어와 책임
| 항목 | 의미 | 위치 또는 도입 조건 |
|---|---|---|
| 백엔드 | API·업무 규칙·권한·저장 처리 | 현재 packages/api와 Next.js API 경로 |
| LLM | 답변을 생성하는 모델 | 현재 Ollama가 실행하고 packages/ai가 호출 |
| RAG | 질문에 관련된 자료를 검색해 모델에 제공하는 방식 | 특정 언어·프레임워크 없이 구현 가능 |
| FastAPI | Python API 서버 프레임워크 | Python 전용 도구나 독립 AI 실행 환경이 필요한 경우 |
| Spring Boot | Java 애플리케이션 서버 구성 | Java 중심 개발·운영 요구가 생긴 경우 |
| Spring AI | Java에서 모델·임베딩·벡터 검색 등을 연결하는 도구 | Spring 기반 AI를 선택했을 때 검토 |
| LangChain | 모델·검색·도구 연결 라이브러리 | 직접 작성한 연결 코드의 복잡성을 줄일 근거가 있을 때 |
| LangGraph | 상태·분기·재개를 포함한 여러 단계의 AI 작업 구성 | 단순 검색·답변을 넘어 반복 검색·검토·승인 흐름이 필요할 때 |

이 도구들을 모두 함께 설치하지 않는다. Spring AI 또는 LangChain을 쓴다는 이유만으로 RAG가 완성되는 것도 아니다.

## RAG 목표 흐름 (계획, 구현 완료 아님)
수집기 → 허용된 자료 정리·중복 제거·출처/날짜/종목 식별자 보존 → 임베딩 → pgvector 저장 → 질문과 종목에 맞는 검색 → core 계산 결과와 결합 → LLM 설명 → 근거 링크·기준일 표시.

- 뉴스는 제목·링크·허용된 요약만 사용하며 기존 본문 저장 금지 원칙을 유지한다.
- 질문과 무관한 최근 기사들을 넣는 현재 방식과 질문 기반 검색을 구분한다.
- embedding 컬럼과 모델 인터페이스만으로 검색 파이프라인이 완료됐다고 표시하지 않는다.
- 임베딩 모델·차원·버전을 기록하고 변경 시 재임베딩/마이그레이션을 계획한다.
- 검색 결과 부족·오래된 자료·누락된 시세를 명시한다. 외부 자료의 지시문을 시스템 지시로 취급하지 않는다.
- 사용자 자료를 검색 대상으로 확장하면 검색 단계에서 소유권 필터를 적용한다.
- 실제 질문 사례로 관련성·출처 정확성·없는 사실을 꾸미는지 평가한다.

## 단계별 순서
1. 금융 데이터 안정화: 이체, 잔액 기준일, 체결 검증, 원자적 저장과 회귀 테스트. 최신 코드에서 반영 여부를 재확인한다.
2. 실사용 완성: 대시보드 정리, 가져오기 이력·되돌리기, 수집 성공/실패 기록, 백업·복원.
3. RAG: 보유/관심 종목 관련 뉴스·공시 검색, 출처·기준일과 함께 답변.
4. AI 사용성: 스트리밍·취소·시간 제한·대화 저장. 독립적으로 가능한 항목은 앞당길 수 있다.
5. 여러 단계 분석: 실제 사용에서 필요성이 확인되면 상태·재시도·검토 흐름과 해당 도구를 선택한다.

## 별도 AI 서버 또는 백엔드 이전을 다시 검토할 조건
- Python 전용 문서 처리·모델 도구가 핵심 기능에 필요하다.
- 추론/임베딩을 별도 장비에서 실행하거나 독립적으로 배포·확장해야 한다.
- 팀의 주력 언어·운영 표준이 Java 등으로 정해진다.
- 현재 API 구조로 처리하기 어려운 장기 작업·권한·운영 요구가 구체화된다.

분리가 필요하면 AI 기능만 별도 서버로 먼저 옮길 수 있다. 예를 들어 apps/ai-server를 두고 기존 API가 호출한다. 언어는 요구사항을 확인한 뒤 선택한다. 로컬 Ollama가 이미 별도 프로세스이므로 모델 실행 분리만을 이유로 중간 서버를 추가하지는 않는다.

전체 백엔드 이전 시에는 REST/OpenAPI 등의 계약, 인증·권한, DB 마이그레이션 책임, 오류/시간 제한/취소, 금액 정밀도, 기존 core 계산과의 결과 동등성을 먼저 정한다. 두 서버가 같은 업무 규칙과 스키마를 각각 관리하지 않도록 소유권을 명확히 한다. 여러 사용자 서비스화는 DATABASE_URL 교체만으로 완료되지 않는다.

## 결과와 범위
현재 구현을 활용하면서 Java/Python 등 후속 선택을 열어 둔다. 이 ADR은 방향과 재검토 조건을 기록하며 새 서버 생성·라이브러리 설치·마이그레이션·RAG 구현을 승인하거나 완료했다고 뜻하지 않는다.
