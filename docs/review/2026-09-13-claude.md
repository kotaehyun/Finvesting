## 2. 코드 검토 (작업 트리)

**좋은 점**
- `core`가 순수 함수로 유지되고 테스트가 따라옴(37개). 요율 계산을 정수 분수로 해서 부동소수 오차 회피
- 계좌×종목 포지션 분리, 재업로드 중복 건너뛰기, `globalThis` 풀 단일화(too many clients 재발 방지) — 운영에서 겪는 문제를 제대로 잡음
- 스키마 `numeric` 문자열 ↔ `Number()` 규칙 일관

**구조적 우려**
- `apps/web/src/app/profile/page.tsx` 1,016줄 단일 클라이언트 컴포넌트에 9개 메뉴 + 20여 개 state + 파일 업로드·다운로드까지. 메뉴별 컴포넌트로 쪼갤 시점(`savings-panel`·`invest-panel`은 이미 분리됨 — 같은 방식으로 master/payroll/fixed/tax/ledger/books 분리)
- `profile` 라우터가 통장 가져오기·템플릿·워드 변환까지 담당. `interop` 관련 프로시저는 `files` 라우터로 분리 권장
- `payroll_months` 스냅샷은 "저장한 달"만 채워짐 → 연봉 추이 12개월은 매달 저장을 안 하면 빈 칸. 통장 거래(`salary` 카테고리 입금)에서 자동 채우는 경로가 없음 — 대장 설계상 급여 입금 거래와 명세서가 연결돼야 "돈의 흐름" 목표에 맞음

- `saveProfile`: `payEarnings` 없이 `monthlyGrossIncome`만 보내면 기존 `pay_earnings`는 남고 gross만 덮어써 `toClient`가 재계산한 gross와 어긋날 수 있음 (`hasEarnings === false` 경로)

## 3. 기획 대비 방향

- Brief의 MVP 1 = Account + Investment. 실제로는 Account·Investment에 더해 **Labor/HR(4단계) 성격의 임금명세서·4대보험·급여전표**와 Savings가 먼저 들어옴. 본인 급여 관리이므로 "근로자 투자자" 페르소나엔 맞지만, 대표 기능(Timeline)과 정보 수집(2단계 기반)이 밀린 것은 사실
- 제안: MVP 1 "완료" 정의를 **본인이 매달 실제로 쓰는 루프**로 고정
  1. 월초 통장·카드 CSV 업로드 → 분류 → 대시보드 현금흐름·배분 가이드 확인
  2. 체결 입력 → 보유 종목 시세 자동(#2) → 원화 평가손익(#3)
  3. 챗봇에 위 두 가지 + 뉴스 + 거시지표가 들어간 상태로 질문
  이 루프가 한 달 돌아가면 그때 Timeline·재무제표 화면으로
- 그 다음 순서 제안: (a) #1~#3 → (b) ECOS·FRED 키 → (c) Financial Timeline(이미 `transactions`·`trades`·`investment_incomes`·`payroll_months`가 있어 뷰만 만들면 됨) → (d) 재무제표 화면
- 미결(Brief §7) 중 "외부 연동 범위"는 사실상 **수동 업로드**로 결정된 상태 — `data-sources.md`나 ADR에 명시하면 이후 AI 세션이 API 연동을 다시 제안하지 않음
