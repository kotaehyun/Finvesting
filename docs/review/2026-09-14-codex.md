## 이해한 제품 방향

Finvesting은 본인인 근로자 투자자를 위한 로컬 개인 금융 터미널이다. 계좌·거래·보유 종목으로 순자산과 월 현금흐름을 계산하고, 시장 수집 데이터와 함께 로컬 LLM이 판단 근거를 설명한다. 급여·예적금·보험·투자성향은 이 개인 재무 상황을 보완한다. 다중 사용자 서비스와 사업자 회계·노무는 후속 단계다.

TypeScript 모노레포에서 core는 계산, interop는 파일 변환, db는 스키마, api는 조합, worker는 수집, web/mobile은 화면을 담당한다. 계좌 잔액은 현금·예수금이고 보유 평가액과 별도로 합산한다. 뉴스 본문은 저장하지 않고, 보험·투자성향은 내부 경험 규칙에 따른 설명이다. 이 방향과 ADR 0007~0010을 유지하는 것이 적절하다.

화면 수는 이미 초기 스캐폴딩을 넘어섰다. 다음 단계는 새 화면 확대보다 **가져오기 → 분류 → 정확한 자산·현금흐름 → 근거 있는 AI 설명**의 완성도를 높이는 것이다.

### 직접 실행한 작은 재현

- core의 `summarizeCashflow`에 자기 계좌 출금 100,000(uncategorized), 입금 100,000(other_income)을 입력하면 income=100,000, variableCost=100,000, spendingRate=1이다. 순이동 0이라도 수입·소비가 각각 부풀려진다. API에서 이체로 수정할 수 없는 것은 코드로 확인했다.
- core의 `buildPositions`에 매도 1주 → 매수 1주 순서로 입력하면 최종 수량은 1, 실현손익은 0이다. 매도가 유효하지 않다는 오류가 발생하지 않는다. 이전 리뷰의 ‘음수 보유’ 표현보다 **잘못된 매도가 계산에서 축소·무시되는 문제**가 현재 구현의 정확한 설명이다.
- 9월 14일 잔액 200,000 → 9월 1일 잔액 100,000 순서의 배열에 현재 잔액 선택식을 적용하면 9월 1일의 100,000을 선택한다. 이 재현은 선택식 실행이며 DB 업로드 통합 테스트는 아니다.

모바일·윈도우는 로컬 웹의 월간 사용 흐름을 안정화한 뒤 확인하는 것이 효율적이다. 지금은 추가 리서치 사이트·사업자 노무·세무 기능 확대보다 데이터 신뢰성과 복구 가능성을 우선한다.

## 잘된 점과 검토 한계

core 계산과 interop 변환이 분리되어 있고 98개 기존 테스트가 통과했다. 계좌별 포지션, 보유/관심 기반 시세 수집, 예수금과 평가액 분리, 보험·성향 규칙을 core에서 계산하는 방향은 유지할 가치가 있다. 문서와 검증 이력이 풍부해 이전 작업을 추적할 수 있다.

이번 검토는 문서·주요 코드 정적 검토와 타입 검사·단위 테스트·작은 계산 재현이다. 전체 파일의 완전한 감사, DB 통합 시험, 브라우저 클릭, 실금융 원장 대조, 외부 API 응답·최신 요율/세법 검증, Ollama 실행, 모바일·윈도우 실행은 하지 않았다. 새 기능과 수정 방향은 제안이며 구현 완료가 아니다.
