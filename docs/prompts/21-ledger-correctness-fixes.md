## 수정할 문제와 완료 조건

### 1. 소수 수량 전량 매도 실패 — P1
위치: packages/core/src/portfolio.ts
- 0.3 매수 → 0.1 매도 → 0.2 매도에서 현재 마지막 매도가 거절돼.
- DB 수량 정밀도(scale 8)와 입력 검증을 함께 고려해 수량 계산 및 잔량 정규화를 수정해.
- 정상 전량 매도는 잔량 0, 평단·환율 초기화가 되어야 해.
- 실제 초과 매도는 계속 거절해야 해. 단순히 모든 초과 매도를 허용하거나 잔량에 맞춰 조용히 축소하지 마.
- 작은 수량·반복 분할 매도·최소 단위 초과 매도·기존 수수료와 환차손익을 회귀 검증해.

### 2. 동일 시각 체결의 검증·저장·조회 순서 불일치 — P1
위치: packages/api/src/routers/trades.ts, packages/api/src/lib/holdings.ts, 관련 DB 스키마
- 생성 검증은 임시 ID new, 이후 검증은 UUID, 보유 조회는 시각만 사용해 동일 시각의 순서가 달라져.
- 영속적인 정렬 기준을 정하고 생성·삭제 검증·보유 조회에서 동일하게 사용해. 실제 저장 ID만 미리 만드는 것으로 경제적 체결 순서까지 해결됐다고 판단하지 마.
- 동일 시각 매수 후 매도, 여러 매수의 다른 가격, 과거 체결 추가, 매수 삭제를 검증해.
- 저장 후 재조회에서도 수량·평단·실현손익이 동일해야 해.
- 스키마가 필요하면 기존 동시각 데이터의 순서를 추측하지 말고 이관 정책과 불확실성을 명시해. 마이그레이션 파일을 만들고 테스트 DB에서 검증해.
- 동시 요청이 동일 잔량을 각각 통과하는지 확인하고 저장 단위의 잠금/직렬화가 필요한 경우 반영해.

### 3. 하루치 내림차순 통장 파일의 잔액 오선택 — P1
위치: packages/core/src/account-balance.ts, packages/interop/src/importers/generic-bank.ts, packages/api/src/routers/transactions.ts, 관련 업로드 UI
- 같은 날짜의 최신 잔액 800 → 이전 잔액 900 입력에서 900을 선택하는 문제가 있어.
- 거래 시각이나 명시적인 파일 정렬 방향을 보존해 최신 잔액을 선택해. 데이터만으로 순서를 알 수 없으면 잔액 자동 반영을 보류하고 사용자에게 이유를 표시해.
- 하루치·여러 날짜의 오름/내림차순, 빈 잔액, 과거 파일 재업로드, 같은 날 일부 과거 거래만 담긴 파일을 검증해.
- 더 오래된 잔액이 현재 잔액을 덮어쓰지 않도록 잔액 기준 시점도 고려해.

### 4. 정상 반복 거래를 중복으로 삭제 — P2
위치: packages/api/src/routers/transactions.ts, 관련 interop/DB
- 같은 날짜·금액·방향·메모·거래처의 실제 두 결제를 모두 보존해야 해.
- 은행 거래 ID를 우선 활용하고 없을 때에는 파일/배치 식별과 출현 횟수 등으로 보존·재업로드 정책을 정의해.
- 단순히 Set을 제거해서 재업로드할 때 전부 중복 저장하게 만들지 마.
- 최초 파일의 동일 거래 2건 보존, 동일 파일 재업로드 추가 0건, 겹치는 기간 파일, 동시 재시도를 검증해. 식별 불가능한 경우를 숨기지 말고 정책에 명시해.
- 중간 실패 시 일부 행이나 잔액만 저장되지 않도록 트랜잭션을 유지해.

### 5. 외화 계좌를 원화처럼 합산 — P2
위치: packages/api/src/lib/overview.ts, accounts API, 현금흐름·계좌별 요약·AI 컨텍스트
- USD 1000을 1000원처럼 합산하지 않도록 수정해.
- 기존 외화 데이터를 보존하면서 현재 지원 범위를 확인하고 환산 정책을 정해. 현재 잔액 평가와 과거 거래 현금흐름에 사용할 환율 기준일을 구분해.
- 환율이 없거나 지원하지 않는 통화는 1:1 환산하거나 조용히 0으로 합산하지 말고 미평가 상태와 합계 제한을 표시해.
- 원화 전용 정책을 선택하더라도 신규 입력 제한만으로 기존 외화 데이터 문제를 해결했다고 간주하지 마.
- 원화·외화 혼합 계좌, 환율 누락, 외화 부채, 월별 현금흐름 및 AI에 전달되는 금액의 일관성을 검증해.
